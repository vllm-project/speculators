# README evaluation report format

Use this structure for a model-card-ready evaluation section. It follows the presentation goals of the Red Hat DSpark model card while requiring enough provenance to reproduce the measurements. Do not copy its checkpoint-specific settings or measured values.

Reference style: <https://huggingface.co/RedHatAI/NVIDIA-Nemotron-3.5-Super-VL-120B-A12B.dspark>

## 1. Evaluation overview

State:

- drafter name and immutable revision;
- base/verifier model and immutable revision;
- speculative method, configured draft length, and adaptive-verification conditions;
- vLLM, Speculators, and AIPerf versions;
- hardware, GPU count, tensor parallelism, precision, and effective context length;
- sampling settings, output cap, prefix-caching state, and selected datasets;
- comparator: native MTP or non-speculative base, including why it was selected.

Describe acceptance length as accepted tokens per verification step including the verifier-contributed token. State that it is neither a percentage nor a measured speedup.

## 2. Acceptance results

Present one pooled request-level table per sampling condition when more than one was actually measured. Build it from `acceptance.csv`. Recommended columns:

| Dataset or category | Successful requests | Acceptance length | Acceptance rate | Pos 0 | Pos 1 |   … |
| ------------------- | ------------------: | ----------------: | --------------: | ----: | ----: | --: |

The adapter's internal position 1 is the first proposed draft token. If the report uses model-card-style zero-based labels, relabel internal position 1 as `Pos 0`, position 2 as `Pos 1`, and so on, and disclose that presentation mapping once.

For SPEED-Bench, also include the two native matrices generated by `aiperf speed-bench-report`:

- `acceptance_length_by_category.csv`;
- `acceptance_rate_by_category.csv`.

These matrices require separate category runs and `server_metrics_export.json` from each run. Their `Overall` column is the arithmetic mean of category values. Native acceptance rates are fractions from 0 to 1; if the report renders them as percentages, convert every value consistently and label the unit. Keep this native category mean distinct from the request-weighted pooled result in `acceptance.csv`. Per-position category rates come from each category run's `acceptance.csv` row.

For other datasets, show one pooled row per native run. Report errors and missing metrics in accompanying text.

## 3. Long-context acceptance

When MRCR was measured, include:

| Prompt-length bin | Successful requests | Mean acceptance length | Acceptance rate |
| ----------------- | ------------------: | ---------------------: | --------------: |

Also state the needle setting, source-row and request budgets, maximum successful prompt length, context-limit failures, and overall pooled values. Keep `unknown` and overflow bins visible when present. Do not describe MRCR acceptance as task accuracy.

## 4. Performance comparison

Introduce the matched configurations before the figures:

- drafter with adaptive verification off;
- drafter with adaptive verification on, when supported;
- native MTP comparator, or the non-speculative base fallback.

Create one comparison figure for every speedup dataset. Each figure should overlay only matched configurations and use one point per measured concurrency. Use:

- x-axis: the explicitly named interactivity statistic;
- y-axis: aggregate output throughput in tokens/second.

The caption must list the dataset, sampling/output cap, hardware/GPU count, tensor parallelism, precision, speculative draft length and adaptive state, comparator, warmup, measurement window, grace period, repetitions, and completed concurrency points.

If reporting a speedup number, define its numerator, denominator, and matched operating point. Do not infer speedup from acceptance length alone. Do not connect or label missing/failed points as though they completed.

## 5. Methodology and artifacts

Briefly document:

- acceptance and speedup dataset budgets;
- how pooled acceptance metrics were calculated;
- interactivity statistic and any offline plot transformation;
- server matching and comparator selection;
- failures, unsupported adaptive/MTP modes, deviations, or incomplete points.

Link the acceptance CSVs, native AIPerf exports, plots, launch/evaluation commands, logs, and provenance manifest in the requested report location. Verify every number and image link against saved artifacts.

## Publication checklist

Before handing off the README:

- all tables are generated from saved records rather than copied from console output;
- pooled request-level metrics use counters, while native category-matrix `Overall` values retain their documented arithmetic mean;
- every plot uses matched settings and correctly labeled statistics;
- every claimed configuration has completed measurements;
- errors and unavailable comparisons are explicit;
- no restricted prompts, credentials, internal hostnames, or raw private payloads are included;
- publishing or uploading occurs only when separately authorized.
