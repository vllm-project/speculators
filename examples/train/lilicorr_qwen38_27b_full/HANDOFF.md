# Handoff: LiLiCorr Qwen3.8-27B run, picking up on a new pod

This is a step-by-step guide for taking over this run on a fresh machine. It
assumes you have **not** seen the rest of this directory before. The full
background/reference doc is [`README.md`](./README.md) — this file is just
"what to actually type, in order."

## 0. What's already been decided, and what's still open

This checkout has uncommitted fixes on top of the public `lilicorr` branch
(base commit `d8c73a887afb39d68daba5a81bd2020585cbc186`). They are **not yet
committed or pushed anywhere** — see [Step 1](#1-get-the-code-onto-the-new-pod)
for how to bring them with you.

**Already fixed / decided (no action needed):**

| Change | File(s) | Why |
| --- | --- | --- |
| Optimizer `muon` → `adamw`, `lr` → `6.0e-4`, scheduler `cosine` → `linear`, `loss_fn` → `ce` | `full.yaml` | Matches the LiLiCorr paper's Table 4 exactly |
| `total_seq_len` → `6144` | `full.yaml` | Agreed compromise between the paper's 3120 and this run's original 8192 |
| DFlash loss normalization now divides by the decay-weighted mask sum, not a raw position count | `src/speculators/losses/utils.py`, `lilicorr/core.py` | Matches NVIDIA ModelOpt's reference; previously under-weighted the loss by ~2.3x at block_size=16/gamma=7 |
| Optional separate LR for the LiLiCorr head (`lilicorr_lr`) | `schema.py`, `trainer.py`, `cli.py`, `optimizers.py` | Not used in `full.yaml` today (unset → same as `lr`), but available via `--lilicorr-lr` if you want to tune the head separately later |

**Still an open decision — read before launching:**

- **`lilicorr_target_source` toggle.** Default is `"argmax"`: both the DFlash
  backbone's CE loss and the LiLiCorr lattice head train against the
  *verifier's own top-1 prediction*, not the real token actually in the
  training data. The paper's reference implementation uses the real token
  (`input_ids`) by default. This only matters because **the training data for
  this run was generated by sampling** (temp 1.0, top_p 0.95, top_k 20 — see
  `README.md` §2), not greedy decoding, so the two genuinely disagree a
  meaningful fraction of the time.
  - This is **not** a YAML/CLI flag — it only exists as a Python kwarg (see
    `get_trainer_kwargs` in `src/speculators/models/lilicorr/core.py`).
  - To turn it on, change the default in that file:
    ```python
    # src/speculators/models/lilicorr/core.py, in get_trainer_kwargs:
    target_source = kwargs.get("lilicorr_target_source", "argmax")  # change "argmax" -> "input_ids"
    ```
  - **Decide this before you launch** — switching it mid-run changes the
    training objective, so a checkpoint trained partly one way and partly the
    other is harder to interpret. If you're not sure, ask whoever owns this
    run; it hasn't been decided as of this handoff.

## 1. Get the code onto the new pod

Pick **one** of these two options.

**Option A — apply the patch to a fresh clone (recommended, cleanest):**

A patch of every uncommitted change in this session is saved at
`/home/MeganEFlynn/lilicorr-paper-fixes.patch` on the old pod. Copy it to the
new pod (e.g. `scp old-pod:/home/MeganEFlynn/lilicorr-paper-fixes.patch .`),


**Option B — copy the whole checkout directly:**

```bash

```

Either way, end up with a `~/speculators` checkout that has `git status`
showing the same modified files as the table in Step 0.

## 2. Sanity-check the new pod before touching anything

**This matters** — the original pod this was planned on turned out to already
have someone else's live job using every GPU. Don't repeat that:

```bash
nvidia-smi
```

Confirm the GPUs you intend to use show `0 MiB` used and `0%` util. If
anything unexpected is running, stop and find out whose it is before
proceeding.

## 7. Launch training

Checkpointing every 5% of an epoch is **already configured**
(`checkpoint_freq: 0.05` in `full.yaml`) — no change needed for that.

Adjust `CUDA_VISIBLE_DEVICES` below to however many GPUs this pod actually
has free (the original run used 2 for the extraction server + 6 for the
trainer = 8 total; scale both down proportionally on a smaller pod, keeping
the trainer side a multiple that FSDP can shard across evenly).

```bash
export PYTHONPATH=~/speculators/src
cd ~/speculators/examples/train/lilicorr_qwen38_27b_full
RUN_DIR=/tmp/lilicorr_check/qwen38-perfectblend/runfull
mkdir -p "$RUN_DIR"

# extraction server — run in background, uses N GPUs
CUDA_VISIBLE_DEVICES=0,1 python ../../../scripts/launch_vllm.py /tmp/models/Qwen3.8-27B \
    --target-layer-ids 4 12 20 28 36 44 52 60 \
    --provenance-dir "$RUN_DIR" \
    -- --data-parallel-size 2 --port 8000 \
    --max-model-len 8448 --max-num-batched-tokens 16384 \
    --gpu-memory-utilization 0.95 --no-enable-prefix-caching \
    > "$RUN_DIR/vllm.log" 2>&1 &

# wait until healthy
until curl -sf http://localhost:8000/health > /dev/null; do sleep 2; done

# trainer — uses the remaining GPUs
PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True,garbage_collection_threshold:0.6 \
CUDA_VISIBLE_DEVICES=2,3,4,5,6,7 python -m torch.distributed.run \
    --standalone --nproc_per_node 6 \
    -m speculators.train --config full.yaml \
    > "$RUN_DIR/train.log" 2>&1 &
```

Watch progress:

```bash
tail -f "$RUN_DIR/train.log"
```

**Do not use plain `torchrun`** — use `python -m torch.distributed.run` as
shown (see `README.md` Gotchas for why this and the other flags above are
load-bearing).

## 8. Wait for the first 5% checkpoint

Checkpoints land at `$RUN_DIR/checkpoints/0/` with an `epoch0_step<N> -> 0`
symlink renamed into place once the write finishes:

```bash
watch -n 30 'ls -la /tmp/lilicorr_check/qwen38-perfectblend/runfull/checkpoints/0/ 2>/dev/null'
```

Note: the original run (at `total_seq_len=8192`) hit its first checkpoint at
step 9,260 (~10.2h). **This run's step count and timing will differ** since
`total_seq_len` is now 6144 — don't assume that number; just wait for the
checkpoint directory to actually appear.

## 9. Compare against the reference at the first checkpoint

Pause the run first (kill the trainer process, then the extraction server —
confirm with `nvidia-smi` that memory is actually freed), then serve the
checkpoint and run the probe:

```bash
CUDA_VISIBLE_DEVICES=0 python -m vllm.entrypoints.openai.api_server \
    --model /tmp/models/Qwen3.8-27B --dtype bfloat16 \
    --max-model-len 2048 --max-num-seqs 4 --gpu-memory-utilization 0.95 \
    --port 8002 --per-request-spec-decode-metrics summary \
    --speculative-config '{"method":"dflash","model":"/tmp/lilicorr_check/qwen38-perfectblend/runfull/checkpoints/0","num_speculative_tokens":15,"draft_sample_method":"greedy"}' \
    > /tmp/lilicorr_check/qwen38-perfectblend/runfull/serve_probe.log 2>&1 &

# after /health is up (~230s on the original A100s; time may vary):
cd ~/speculators/examples/train/lilicorr_qwen38_27b_full
python probe_acceptance.py   # saves runfull/acceptance_probe.json
```

**This needs the vLLM fork's speculative-decoding config support** — branch
`lilicorr-speculators-config` on `github.com/MeganEFlynn/vllm` (see
`README.md` §0 for exact checkout commands). Training itself doesn't need
this; only this probe step does.

Compare your `acceptance_probe.json` numbers against the reference, measured
at the original run's first 5% checkpoint (`README.md` §7):

| Metric | Reference (step 9260, old 8192-seq-len run) |
| --- | --- |
| Token-weighted acceptance length | 2.73 |
| Draft-token acceptance rate | 11.5% (1,869 / 16,200) |
| Rounds accepting ≥ 1 of 15 | 67.7% |
| Per-prompt AL range | 1.91 – 4.63 |

Exact equality isn't expected — the sequence length, optimizer, LR, loss
function, and loss normalization are all different from that reference run
(see the table in Step 0). The useful comparison is **order of magnitude and
shape**: acceptance length clearly above 1.0 and rising, no sign of
divergence in `train.log`'s loss curve. If it's wildly off (e.g. AL stuck
near 1.0, or loss exploding), stop and investigate before continuing — don't
assume it'll fix itself with more steps.

## Key gotchas (full list in `README.md`)

- `/tmp` is ephemeral on most pods — copy anything you want to keep off of it.
- `draft_attn_impl: sdpa` and `loss_chunk_anchors: 128` in `full.yaml` are
  load-bearing for memory at this model scale — don't remove them.
- The extraction server's `--max-model-len 8448` and `--no-enable-prefix-caching`
  flags are required, not optional (see `README.md` Gotchas for why).
