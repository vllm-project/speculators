# Target-Source Comparison: `input_ids` vs `argmax` — HumanEval per-position acceptance

Purpose: hold the served-eval results needed to compare LiLiCorr training with
observed `input_ids` targets against `argmax` targets, at matched recipe and
training progress. The `input_ids` side is filled in below; the `argmax` side
will be filled in when that run reaches the same point.

Background: the LiLiCorr ground truth for the backbone CE and the lattice
terms can be defined either as the token actually sampled into the training
sequence (`input_ids`, ModelOpt's reference default) or as the verifier's
argmax token (`argmax`, a hard-distillation choice). Our training corpus was
generated by *sampling* (temp 1.0, top_p 0.95, top_k 20), so the verifier's
argmax routinely disagrees with the realized token — the two settings train
against measurably different targets. Run 1 (EXPERIMENTS.md §2) used argmax
but never produced a valid HumanEval number (eval-server bug), so this
comparison starts clean with Run 3.

## Shared recipe (both sides)

plan.md recipe: fresh 5-layer draft, block 8 (7 speculative tokens),
candidate K=8, gamma 3, seq len 8192, Muon+AdamW @ 6e-4, cosine over 2 epochs,
4% warmup, pure CE + lattice CE 0.25 / penalty 0.25, `checkpoint_freq 0.25`,
FP32 checkpoints. Verifier Qwen3.8-27B; HumanEval via `evaluate.py`
throughput mode, default sampling temperature, `draft_sample_method=greedy`.
Only difference between sides: `lilicorr_target_source`.
